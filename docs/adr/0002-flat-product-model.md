# Flat Product model, no separate Variant entity

Each flavor/format of a brand's line (e.g. "Fancy Feast Gravy Lovers Chicken" vs "Fancy Feast Gravy Lovers Salmon") is its own top-level Product row with a `variant` attribute, rather than a normalized Product → Variant hierarchy. We picked this because all three candidate data sources (Open Pet Food Facts, the Chewy dataset, and the manually-curated set) are already naturally shaped as one row per SKU, and a "division" query ("brands offering every variant across their line") is answerable by grouping flat Product rows by brand and checking variant coverage — no join to a child table required. A reader expecting a normalized hierarchy (implied by "variant" language in earlier planning docs) should know this was a deliberate simplification, not an oversight.
